## 已确认的选择

- 成员通过 Sharey Skill 和 CLI 访问服务；CLI 调用 FastAPI 提供的 HTTP API，服务端负责已发布 Git 节点的校验与持久化，并统一处理项目凭证、项目导航与内容获取。
- 首轮验收在本机运行服务，由两个隔离的成员环境与两种 Agent 访问；按照产品定义验证上下文接续、完整 Skill 执行、研究分支与汇合、发布快照及重启持久化。
- 首个样例以 Markdown、代码、配置、小型结果表、论文与完整 Skill 为主。大型数据提供说明和可访问地址，首轮不以大型数据本体传输为验收要求。
- 发布默认保存明确选定文件当时的磁盘内容，允许未提交修改与未跟踪文件；使用 Git 的成员无需先提交。Git 来源信息需要与实际发布内容一致。
- Sharey 是成员驱动的 Agent 与自主 Agent 共用的研究协作基座；自主执行、任务协调、实验评价与停止由外部 Agent 运行环境承担。
- 每个研究节点直接对应 Git commit，commit parents 表达研究派生关系，节点通过独立且不可变的 ref 保留。取舍见 [ADR-0001](adr/0001-research-nodes-as-git-commits.md)。
- 成员原有工作代码仓库与 Sharey 项目仓库分别管理各自的数据和历史。Sharey 从明确选定内容创建独立发布快照，原仓库继续负责可编辑的工作文件；两者不做双向状态同步。取舍见 [ADR-0002](adr/0002-independent-working-repositories-and-publication-snapshots.md)。
- 首版客户端通过 HTTP 按需查询、读取、下载与发布，不长期维护 Sharey 项目的 Git clone；客户端不要求安装 Git。Git 是服务端保存研究节点及派生关系的实现工具。

## 实现草案

以下是基于已确认边界的具体实现方案与工程默认值；尚未编写或运行产品代码。调研依据见 [团队协作与多 Agent 研究基座](research/team-and-multi-agent-foundation.md)。

### 复用工具与模块

使用一个 Python 包承载服务端和 CLI，复用 FastAPI、Uvicorn、Pydantic、HTTPX，以及标准库的 argparse、zipfile 和 subprocess。服务端通过 Git 原生命令创建和读取对象、commit 与 refs；首版不实现 Git 网络传输，也不需要 Git 托管平台。

项目使用 uv 管理独立的 Python 3.12 环境与依赖，在实现时生成锁文件。2026-10-11 的本机只读检查显示系统 Python 是 3.9.6、uv 是 0.10.6、Git 是 2.50.1；项目不直接依赖系统 Python 安装环境。FastAPI 与 Uvicorn 的启动关系、HTTPX 的请求与文件能力、标准库模块职责已核对官方文档：[FastAPI 手动运行服务](https://fastapi.tiangolo.com/deployment/manually/)、[HTTPX QuickStart](https://www.python-httpx.org/quickstart/)、[Python 标准库](https://docs.python.org/3/library/index.html)。

- CLI 负责参数解析、读取明确选定的文件、生成发布包、HTTP 请求与将获取内容保存到指定目录。
- 服务端领域层负责项目访问资格、节点与资产元数据、父节点及引用校验、发布与概览。
- Git 存储模块负责文件对象与 tree、commit、固定 refs 和对象读取；共享发布原语也供来源材料及完整 Skill 使用。
- Sharey Skill 指导成员自己的 Agent 编译研究记忆、选择材料、调用 CLI、引用依据并接续研究。

### 服务端数据布局

每个项目一个 bare Git 仓库，保存在显式配置的持久数据目录中。项目目标与项目凭证由部署者初始化；凭证通过服务端配置提供，不写入共享 Git 内容。首个验收只配置一个项目。

| 对象 | Git 表达 | 内容与读取方式 |
| --- | --- | --- |
| 研究节点 | 独立 commit；parents 仅指向同项目已发布研究节点 | tree 保存 `metadata.json`、`memory.md` 与 `files/`；节点标识、父关系及发布时间由发布结果和 Git 信息提供 |
| 来源材料 | 独立、只读资产 commit | 元数据与实际文件；可列出、读取、下载 |
| 完整 Skill | 独立、只读资产 commit | 元数据与完整 Skill 目录；获取后保持 `SKILL.md` 及资源的原相对路径 |
| 项目概览 | 从已发布节点与资产生成的视图 | 返回项目目标、节点摘要、父关系与资产索引，不维护另一份研究历史 |

各类对象使用独立的 ref 命名空间。创建对象与 commit 后才原子创建对应 ref，使半成品不可见；refs 只允许新建，已发布对象不覆盖。构建 tree 使用独立暂存或 Git 对象命令，不争用同一个工作树或 index。重试同一次发布应返回原发布结果，避免网络超时导致重复节点。具体 ref 命名和请求幂等键格式在编码时确定。

### 最小 CLI 与 HTTP 接口

下表中的命令是建议接口，尚未实现。CLI 通过环境变量或显式参数取得服务地址、项目与凭证；不需要在成员原代码仓库写配置。

| CLI 操作 | HTTP 能力 | 返回或落盘内容 |
| --- | --- | --- |
| `sharey overview` | 获取项目概览 | 项目目标、节点摘要及派生关系、来源材料与 Skill 索引 |
| `sharey list nodes/sources/skills` | 列出对应对象 | 简短元数据与稳定标识 |
| `sharey show node <id>` | 读取节点 | 节点元数据、研究记忆与文件清单 |
| `sharey get file <node-id> <path> --out <path>` | 获取具体文件 | 原始文件内容 |
| `sharey get node <id> --out <dir>` | 获取节点文件包 | 研究记忆、元数据和选定文件 |
| `sharey get source <id> --out <path>` | 获取来源材料 | 原始材料文件 |
| `sharey get skill <id> --out <dir>` | 获取完整 Skill | 可被 Agent 读取和运行的完整目录 |
| `sharey publish node --manifest <path>` | 发布节点文件包 | 新节点标识与父节点关系 |
| `sharey publish source --file <path>` | 发布来源材料 | 来源材料标识 |
| `sharey publish skill --dir <path>` | 发布完整 Skill | Skill 标识 |

HTTP 路由按 `/projects/{project}/` 组织，提供 overview、各类对象的列出/读取/发布，以及文件和归档获取。来源材料及 Skill 与节点读取使用同一项目凭证。

节点发布清单由 Agent 编译生成，列出标题、短摘要、署名、研究记忆文件、研究父节点、选定源文件到节点相对路径的映射，以及来源材料和 Skill 引用。CLI 只打包清单中明确列出的内容；完整 Skill 发布则以选定的整个 Skill 目录为单位。使用 ZIP 传输文件集合，服务端验证条目路径与引用后创建 Git 对象。

下载使用显式目标路径；节点材料与完整 Skill 保持独立目录。CLI 不自动覆盖既有工作文件，也不自动将 Skill 安装到某厂商 Agent 的全局目录。Agent 根据当前任务决定如何读取、运行或选用这些内容。

### 启动与验证顺序

首版提供本机服务启动入口，使用 Uvicorn 单进程运行 FastAPI，显式指定持久数据目录、项目与访问凭证。自动化测试使用临时目录、真实 Git、真实 HTTP 和两个独立客户端工作区；当前功能实现无需云服务器、GPU 或科研数据集。

当前交付顺序如下，所有验证仍待执行：

1. 使用 pytest、FastAPI TestClient、真实 Git 与临时文件验证产品契约：选定文件的原始字节、完整 Skill 相对目录、不可变节点、多父关系、无效引用、凭证及未选文件边界。另检查发布 dirty/untracked 文件后，原工作仓库的文件、HEAD、index 和配置不变。
2. 使用真实 HTTP 与 CLI 子进程验证端到端操作；并发发布不能丢失节点，同一发布重试不能重复。实际终止、重启服务并验证持久化；在发布关键阶段中断，检查没有可见半成品且已确认的发布仍可读取。
3. 提供固定的小型测试项目，包含研究记忆、文本与二进制文件、一份来源材料及带脚本和相对资源的完整 Skill。由两个独立客户端执行发布、查询、下载、实际运行 Skill、分支与双亲汇合；逐项检查最终内容和关系。脚本驱动的测试明确标为 CLI 功能验证。
4. 功能完成后，用可用的两种实际 Agent 执行小型上下文接续与 Skill 使用验证；不要求运行真实科研实验。登录或模型接入状态只影响实际 Agent 验证，不阻碍服务、CLI、Skill 与自动化测试的开发。未执行时在验收记录中明确标为待验，不能用两个 CLI 工作区代替跨厂商 Agent 通过。
5. 真实科研任务、GPU 实验、重复科研回合和收益对照放到后续。现有 [正规测试与验收调研](research/testing-and-acceptance.md)及[自动化 AI 研究调研](research/automated-ai-research-acceptance.md)作为后续设计资料保留。

以下细节由实现阶段落实，不再作为等待产品决策的事项：

| 事项 | 首版默认 |
| --- | --- |
| 项目初始化 | 部署者在服务端配置项目目标、标识、凭证和持久目录；先提供一个项目的完整使用入口 |

## 成员已有代码仓库与 Sharey 仓库的关系

以成员 A 的 `A/some-research` 为例，它继续作为 A 的工作代码仓库；Sharey 项目仓库保存明确发布的研究快照。两者是独立的 Git 仓库，关联是从工作目录发布选定内容，以及在研究节点中记录可追溯的出处。

一次发布从 `some-research` 读取选定文件当时的内容，连同 Agent 编译的研究记忆创建新的 Sharey commit。研究父节点指向已有 Sharey 节点；原仓库路径或地址、可用的代码 commit 基线、选定路径及相对该基线的变化情况属于出处信息，不自动成为研究父节点。节点内实际保存的文件是本次发布内容的依据。

因此，原代码仓库的提交和 Sharey 发布各自演进。队友可以获取已发布文件继续研究并发布派生节点；将这些工作集成回 `some-research`，仍是一次明确的代码修改与 Git 集成操作。Sharey 保存发布副本，成员无需手工维护第二套源文件。

正在编辑的文件只由原工作仓库维护。发布时读取文件并构造独立快照，Sharey 的 Git 存储与任何客户端暂存、缓存都使用自己的目录；Sharey 不在原工作目录中建立另一套 Git 管理状态，也不修改其 index、HEAD 或 remotes。客户端清理自己的暂存或缓存不会删除原工作文件。

成员只维护原代码仓库的工作状态，并在需要分享时发起研究发布。原文件修改后，旧节点继续表示上次发布时的状态；再次分享形成新节点。两者的内容差异是工作进展与发布历史的差异，无需保持双向一致。队友获取的材料只有经过明确选用，才进入其现有工作目录。
