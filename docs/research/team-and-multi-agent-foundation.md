# Sharey：团队协作与自主多 Agent 研究基座

调研日期：2026-10-11。状态：**架构研究与设计推断，待用户决定**。依据当前 [产品定义](../product-definition.md)、[实现方案](../mvp-implementation-plan.md) 与 [领域词汇](../../CONTEXT.md)，核查 4 个一手来源。本文没有实现 Sharey，也没有运行所述 Agent 系统；以下验证场景是提案，不是验收结果。

## 结论

**Sharey 可以成为人类研究团队与自主多 Agent 共用的研究成果、上下文和方法基座。建议复用同一套读取、获取与发布接口，让已有 Agent 运行环境负责启动、分工、执行和停止。**

用户的直觉抓住了关键共性：两种协作都需要参与者获取已有研究状态，独立工作，再发布带依据的新状态。参与者由成员指挥的 Agent 换成预先授权的自主 Agent，研究节点、材料、Skill、父节点关系和项目概览仍然适用。

但“完全相同的功能就能支持”需要明确所指。**对 Sharey 的共享接口，可以相同；对整个自主研究系统，只有这些接口还不够。** 人类团队中的任务选择、资源安排、异常处理和判断结果是否可信，原本由人和成员自己的工具承担。自主运行后，这些职责仍然要有承担者，可以是现有 Agent harness、执行脚本或约定，不必搬进 Sharey。

## 一手来源支持的机制

### 1. Anthropic 的编译器实验：共享 Git 确实能支撑自主多 Agent 协作

2026-02-05 的工程报告使用一个 bare Git 仓库；每个 Agent 在独立 Docker 容器内 clone 工作副本，然后同步、合并与 push。任务通过 `current_tasks/` 文件认领，竞争由 Git 同步暴露。作者明确没有使用编排 Agent。另外，实验配置了持续运行循环、测试及反馈机制。[Anthropic：Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)

**对 Sharey 的推断：**“用同一个 Git 项目支撑多人或多 Agent”是有实际案例的设计方向。这个案例也说明，Git 存储和同步之上仍有任务认领约定与执行环境；不能把整个效果归给共享仓库。Sharey 可以借用相同机制，而无需先引入一个中心调度系统。

### 2. Anthropic Research：任务分工与持久研究产物可以分开

2025-06-13 的工程报告采用 lead agent 分解问题、启动并行 subagent、汇总结果的结构。报告还建议 subagent 将产物直接存入外部系统，再向协调者返回轻量引用；其委派规则说明目标、输出格式和任务边界，以减少重复工作。[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

**对 Sharey 的推断：**Sharey 可以承担这里的外部研究产物系统。一个现成 Agent team 可以调用 Sharey CLI 读取父节点，完成研究后发布新节点，再把节点标识交给其他 Agent。它无需把完整文件或全部聊天历史经过主 Agent 转述。这里的 lead agent 是一种可用方式，不是所有多 Agent 系统的必要架构。

### 3. A2A：正在执行的任务与输出产物是不同对象

A2A v1.0.0 将 `Task` 定义为带状态的行动单元，含 working、completed、failed、canceled 等状态；`Artifact` 表达输出。规范另有任务查询、取消和状态更新操作。[A2A v1.0.0：Task 与 Artifact](https://a2a-protocol.org/v1.0.0/specification/#41-core-objects)、[任务操作](https://a2a-protocol.org/v1.0.0/specification/#31-core-operations)

**对 Sharey 的推断：**当前研究节点适合保存一次已发布的研究状态和文件快照，不能直接充当运行中的任务。某次任务可能失败而没有发布，也可能多次发布中间结果。若未来接入 A2A，可将任务输出保存为 Sharey 节点并返回引用；本次无需为了复用这个思想实现 A2A。

### 4. AI Scientist-v2：研究树与推动树增长的执行规则同时存在

官方仓库说明其采用 experiment manager 引导的渐进式 agentic tree search。配置将 `num_workers` 用于并行探索数量，`steps` 用于最多探索的节点数，`max_debug_depth` 用于失败节点的调试次数上限。[Sakana AI：AI-Scientist-v2 官方仓库](https://github.com/SakanaAI/AI-Scientist-v2#run-ai-scientist-v2-paper-generation-experiments)

**对 Sharey 的推断：**研究状态可以形成树或 DAG，但存储派生关系本身并不决定下一步探索哪个分支、并行多少实验、失败后重试几次。已有自动研究系统可以承担这些选择；Sharey 保存它愿意共享的输入、结果、依据与方法。这里没有证据证明套用一个自动研究框架就能成功完成任意科研项目。

## Sharey 的设计推断

### 同一套共享功能可以服务两种参与方式

下表是设计映射，不是一手来源对 Sharey 的实现结论。

| 协作动作 | 成员驱动的 Agent | 自主 Agent | Sharey 是否需要另一套功能 |
| --- | --- | --- | --- |
| 了解项目与已有进展 | 成员要求 Agent 查询 | 运行任务中的 Agent 自行查询 | 不需要，同一项目概览与读取接口 |
| 获取依据与工作方法 | Agent 获取材料、完整 Skill | Agent 获取材料、完整 Skill | 不需要，同一获取接口 |
| 独立探索 | 成员和 Agent 决定下一步 | 外部运行环境、Agent 或预定规则决定下一步 | 研究执行继续留在 Sharey 外部 |
| 发布研究状态 | 成员明确要求分享选定内容 | 在成员预授权的范围内分享产物 | 可以使用同一发布接口 |
| 接续或汇合 | Agent 基于已有节点工作 | 自主 Agent 基于已有节点工作 | 不需要，同一父节点关系 |

建议的职责分工如下。图示不决定具体框架，也不要求中心编排 Agent。

```text
成员指挥的 Agent                 预先授权的 Agent team / 研究循环
       │                         │
       │                启动、分工、实验执行、预算与停止
       │                         │
       └───────── 同一 Sharey Skill / CLI ─────────┘
                            │
                 项目概览、材料、研究节点、完整 Skill
                            │
                    Sharey 服务与持久存储
```

### 用两个具体反例检验“同构”

**反例一：两个 Agent 都从父节点 R 开始，分别发布 A 和 B。** 两份内容放在独立、发布后只读的节点中，父节点都写 R，可以自然表达并行探索。之后某个 Agent 读取 A、B，整理后发布父节点为 `[A, B]` 的 C。这与两位研究成员的分支与汇合完全一致。存储层仍须正确处理并发发布，保证两次写入都被保留；这是发布接口的正确性问题。

**反例二：两个 Agent 都决定跑同一个昂贵实验。** 它们也可以顺利发布 A 和 B，DAG 完全合法，但算力已重复消耗。研究节点的派生关系没有提供实验认领。若持续循环又没有上限，即使所有发布都正确，费用仍然会增长。这需要任务分工、认领约定或预算控制；可以借用外部运行环境已有能力，也可以像编译器案例一样用 Git 文件约定，按实际场景选择。不能由此推出 Sharey 必须内置调度器或租约系统。

这两个反例表明：**共享研究状态相同，不等于整个协作过程由研究 DAG 保证。** 人类团队也会重复劳动，区别在于人常常通过开会、口头约定或实验排期补上协调。自主 Agent 需要可执行的替代方式。

### 显式发布与自主发布能够保持同一边界

当前产品定义要求成员明确分享的内容才进入项目。自主运行可以在开始时取得明确授权，例如：

> 在项目 P 中，从节点 R 开始，用指定目录中的材料运行这组实验；允许将本次输出目录的实验结果、配置和研究记忆发布到 P，最多运行两次实验，完成后停止。

这是一种**限定范围的预授权**：允许 Agent 在这次工作中自己选择何时发布，不等于把所有私人内容自动共享。成员驱动和自主运行仍可调用同一发布接口。具体如何表达和落实授权，属于后续 Agent 接入设计；本研究不增加全平台自动发布承诺，也不把持有项目凭证等同于获得发布任意本地文件的授权。

### Git 能同时作内容底层，但要保留研究语义

Git 可以存储项目共享文件、研究记录、Skill，也能承载额外的协作约定。客户端是否使用 Git，是实现取舍；谁决定分享什么，是产品语义。将普通目录中选定文件暂存到 Sharey 管理的 Git 工作区并提交，仍符合“发布当时选定的内容”，也不要求成员的原仓库先提交。

研究节点的父节点关系应继续表达研究依据。成员或 Agent 后到达服务端，并不意味着其研究基于先到达的节点。Git 原生允许 commit 有多个父节点，并可直接用指定文件树与父节点创建 commit，因此“研究节点即 commit”是成立的候选；另一候选是在项目目录中追加节点并在节点元数据保存研究父节点。底层 Git 图与研究派生 DAG 是否一一对应，取决于这项布局选择。[Git：git-commit-tree](https://git-scm.com/docs/git-commit-tree)

**本轮已执行的 Git 机制验证：**在 `/private/tmp` 的临时 bare 仓库中，通过 `hash-object`、`mktree`、`commit-tree` 创建 R（无父节点）、A（父 R）、B（父 R）、C（父 A、B），再用 `update-ref` 分别保留 `refs/records/R`、`A`、`B`、`C`。实际读取 commit 父节点得到 `R:[]`、`A:[R]`、`B:[R]`、`C:[A,B]`；四个 refs 均存在，创建 C 后读取 `R:memory.md` 仍是 R 的原快照。临时目录随后移除。这证实 **Git 本身可以直接表达该研究 DAG**，因此不能断言研究父节点必须另存一套元数据。它没有验证 Sharey 产品实现、客户端同步、并发发布或多 Agent 执行。

## 最小验证场景

建议先完成现有 MVP 验收，再以一个可复用的小场景检验“同一接口能否支持自主参与”。以下是后续验证提案，不新增本次必交功能。

1. 成员发布父节点 R，内容包含小型 CSV、问题说明与完整分析 Skill；明确允许这次 Agent team 将指定输出目录的内容发布到该项目。
2. 使用已有 Agent 运行环境启动两个 Agent，分别处理预先分开的分析问题；各自读取同一个 R、获取同一个 Skill，在独立目录运行，分别发布 A、B，父节点都为 R。
3. 其中一个 Agent 读取 A、B 及其结果文件，发布汇合节点 C。检查它能指出两个分析的具体证据，而不只是生成概括性叙述。
4. 检查两次并发发布都保留、R 未变化、未授权的文件未发布。复用现有重启持久化检查即可。
5. 单独做一次重复任务试验：让两个 Agent 看到相同实验要求，观察现有运行环境或任务约定能否避免重复。将“研究材料成功共享”与“实验只执行一次”分别记录，避免用前者代替后者。

记录应包含实际 Agent 与运行环境、输入节点、输出节点、Skill 执行结果和实验次数。只有完成步骤 1–4，才能支持“同一 Sharey 接口适用于该自主协作样例”；步骤 5 检验的协调能力归于实际承担它的机制。这个小样例不能证明通用自动科研能力或科研结果质量。
